# 31 Nights of Halloween Movies

**Live:** https://31nightsofhorror.com

A horror-movie advent calendar for October. There's one film for each night of the month. Visitors pick a date on the calendar, read about that night's movie, rate it from 1 to 5 blood drops, see the community's average, and discuss it in threaded comments. The list is also published on [Letterboxd](https://letterboxd.com/snowkempm/list/31-nights-of-halloween-whore-movies/).

## Stack

| Concern        | Choice                                                                  |
| -------------- | ----------------------------------------------------------------------- |
| UI             | React 19 + TypeScript, built with Vite; plain CSS with design tokens    |
| UI state       | `useReducer` + React context, event-based                               |
| API            | Go (standard library `net/http`), hexagonal architecture                |
| Database       | Postgres on **Neon** (free plan); `golang-migrate` + `sqlc`             |
| API hosting    | **Google Cloud Run** (scales to zero, free tier)                        |
| Site hosting   | **Cloudflare Pages**; a Pages Function proxies `/api/*` to Cloud Run    |
| Images         | **Cloudflare R2** at `images.31nightsofhorror.com`                      |
| DNS            | **Cloudflare** (the domain's existing DNS provider)                     |
| Anti-spam      | **Cloudflare Turnstile** on comment posting                             |
| Infrastructure | **Terraform** (Cloudflare, Google, Neon providers)                      |
| CI/CD          | **GitHub Actions** and a `Makefile`; both run the same commands         |

Target cost: **$0/month**. Every piece runs inside a free tier at this site's traffic. See [Infrastructure decisions](#infrastructure-decisions).

## Running locally

There are two ways to run everything. They are equivalent: the site is on http://localhost:3000, the API on http://localhost:8080 and Postgres on localhost:5433.

**With containers** (needs Docker Desktop):

```bash
make up            # docker compose up --build --watch
make down          # stop; `make reset-db` also wipes the local database
```

`compose.yaml` runs Postgres 17, the Go API (built from `go/Dockerfile`) and the Vite dev server (`ts/Dockerfile.dev`). With `--watch`, editing Go code rebuilds the API container, and editing the site syncs into the Vite container for hot reload. Posters are served from `assets/` by the API.

**Without containers** (needs Go 1.26+ and Node 22+):

```bash
make dev           # or ./start.sh
```

This starts three things, and Ctrl-C stops all of them:

1. **Postgres** on `:5433`: an embedded binary, with data kept in `.dev/pgdata`.
2. **The Go API** on `:8080`. It runs migrations on startup, which also seed the 2025 lineup.
3. **Vite** on http://localhost:3000. It proxies `/api` and `/images` to the API, so the browser sees one origin, the same as in production.

Local development uses Cloudflare's always-pass Turnstile test keys, so comments work without an account.

`./start.sh --prod` serves a production build of the site instead. You can also run just the site with `npm start` in `ts/`, pointed at an API that is already running. To test on phones, see [docs/mobile-testing.md](docs/mobile-testing.md).

```bash
make test          # all Go + TypeScript tests (Go integration tests start their own Postgres)
make generate      # regenerate sqlc code after editing any .sql query or migration
make e2e           # Playwright browser tests (uses your installed Chrome) against the running stack
```

## Architecture

```
 Browser ──▶ Cloudflare (DNS, CDN, TLS)
               ├── 31nightsofhorror.com ─▶ Cloudflare Pages ── static React build
               │                             └── /api/* ─▶ Pages Function (proxy) ─┐
               └── images.31nightsofhorror.com ─▶ R2 bucket (posters)             │
                                                                                   ▼
                                                     Google Cloud Run: Go API (scales to zero)
                                                                                   │
                                                                                   ▼
                                                                  Neon Postgres (scales to zero)
```

### Why the API is proxied through Cloudflare

The site and API share one origin (`31nightsofhorror.com/api/...`). That has three benefits:

- The visitor cookie is first-party and `HttpOnly`.
- The browser needs no CORS setup.
- Cloud Run needs no custom domain.

The Pages Function (`ts/apps/web/functions/proxy.ts`) copies the visitor's IP and country into `X-Client-IP` and `X-Client-Country` headers for the API.

### Go API: hexagonal architecture

Dependencies point inward:

```
cmd/api (wires everything)
   │
   ├── adapter/httpapi ──▶ app (use cases) ──▶ domain
   │        (driving)          │
   │                           ▼ ports (interfaces declared in app/port.go)
   └── adapter/postgres ───────┘  (driven: implements MovieRepository, RatingRepository, EventRepository)
```

- **`domain`** has no imports from storage or HTTP. It holds the rules: movie IDs look like `2025-07`, ratings are 2/4/6/8/10, and analytics events are validated and clamped.
- **`app`** contains the use cases:
  - `Catalog.Movies` returns a whole year's lineup with ratings in one call.
  - `Ratings.Rate` saves a rating.
  - `Analytics.Track` and `Analytics.Record` store events.

  They depend only on port interfaces.
- **Adapters** implement the ports. `httpapi` depends on the use cases through small interfaces, so its tests use stubs. The Postgres adapter is tested against a real Postgres.
- **`cmd/api/main.go`** is the only place that knows about every adapter.

`cmd/api` subcommands: `api` serves HTTP, `api migrate` applies migrations and exits, and `api comment-status ID hidden` moderates a comment.

### Anonymous visitors

There are no accounts. A visitor's first API request (the `page_view` event) gets a random visitor ID in an **HMAC-signed, HttpOnly cookie** (`vid`), which lasts 400 days. Every API response re-sends it, so the 400 days count from the visitor's *last* visit (a sliding expiry), and the same browser keeps one identity across sessions and days. The server sets it as `HttpOnly` from the site's own origin, so Safari's 7-day limit on script-set cookies doesn't apply. A forged or tampered cookie is replaced. Ratings (one per visitor per movie) and comment authorship are keyed on this ID. This replaces Firebase anonymous auth.

### Analytics: every site event is stored

All events go into one append-only Postgres table, `events`.

- **From the browser** (`ts/apps/web/src/lib/analytics.ts`):
  - `page_view` is sent **as the first request of every visit**. It also establishes the visitor cookie and wakes Cloud Run and Neon if they're idle, before the movies load.
  - Later events (`day_selected`, `calendar_toggled`, …) are batched, up to 25 per request. Anything still queued when the page is hidden goes out with `navigator.sendBeacon`.
- **From the server:** `rating_saved` and `comment_posted` are recorded by the use cases themselves.
- **Stored per event:** type, source (`client` or `server`), visitor, session, path, referrer, user agent, country, JSON `props`, the client's time (clamped to ±24h of server time) and the server's receive time.
- **Not stored:** raw IP addresses.
- **Failures are contained:** analytics can never break a feature. Server-side recording errors are logged, not returned, and the browser client swallows network errors.

### Comments: a reusable threaded module

`go/pkg/comment` and `ts/packages/comment` are designed to be reused in other projects.

- **Tree storage:** an **adjacency list** (`parent_id`). Postgres returns a page of top-level comments with all their replies in one `WITH RECURSIVE` query. The core's `BuildTree` then orders them: newest conversations first, replies oldest first.
- **Attaches to anything:** comments hang off a **thread key** chosen by the host app (`movie:2025-07` here). The module knows nothing about movies. The host app supplies identity through an `Identity func(*http.Request)`, and human verification through the `Verifier` port.
- **Built-in rules:**
  - 1–2000 character bodies, with an optional name of up to 40 characters.
  - At most 5 levels of nesting.
  - A limit of 5 comments per visitor per minute.
  - Authors can delete their own comments; moderators can hide any comment.
  - A hidden comment that has replies stays in the thread as a `[removed]` placeholder.
- **Own migrations table:** the module tracks its schema in `comment_schema_migrations`, so its versions never clash with the host app's.
- **Adapter contract:** every storage adapter must pass `pkg/comment/storetest`. Both the in-memory and Postgres stores run it.
- **UI:** `<CommentThread threadKey=… />` renders the tree, with reply forms, delete and "load older". `useTurnstile(siteKey)` supplies the anti-spam tokens. The site only mounts a thread when a visitor opens a movie's comments.

To moderate, run `api comment-status <id> hidden`. To undo, run `api comment-status <id> visible`.

### Database and migrations

- **Migrations** are `golang-migrate` files (`NNNNNN_name.up.sql` / `.down.sql`), embedded in the binary and applied on startup. A Postgres advisory lock keeps concurrent Cloud Run instances safe. The app tracks its version in `schema_migrations`, and the comment module in `comment_schema_migrations`.
- **Queries** are written in SQL (`queries.sql`), and **sqlc** generates typed Go in `internal/db`. CI fails if the generated code is stale (`make check-generated`).
- **Tables:**
  - `movies`: id `2025-01`, year, day, date, title, directors, description, poster_path, and so on.
  - `ratings`: primary key `(movie_id, visitor_id)`, with the value checked to be one of 2/4/6/8/10.
  - `events`
  - `comments`
- **Lineups are data migrations.** The 2025 lineup is `000002_movies_2025.up.sql`. A new year means:
  1. Add a migration for the new lineup.
  2. Put its posters in `assets/posters`.
  3. Run `make upload-posters`.
  4. Bump `VITE_LINEUP_YEAR`.
- **Movie IDs include the year**, so the 2026 lineup never inherits 2025's ratings.

### Tests

Code is written test-first (TDD).

- **Go:** domain and use cases are tested with in-memory fakes. Adapters are tested against a **real Postgres**: `pkg/pgtest` starts an embedded Postgres 17 binary (no Docker), and each test gets its own fresh database. Set `PGTEST_URL` to use an existing server instead. A migrations test also checks that every `down` migration reverses its `up`.
- **TypeScript:** Vitest + Testing Library. This covers the reducer, the API and analytics clients, the Pages proxy, the comment thread UI, and a whole-page `App` test with fake services.
- **Browser (e2e):** Playwright in `ts/apps/web/e2e`, run against the live local stack at desktop and phone sizes. It covers the main flows and guards the hero title against rendering in a fallback font.

### UI state: reducer + events

All UI state lives in one store (`ts/apps/web/src/state/reducer.ts`): `movies` (loading/ready/failed and the lineup), `calendar` (selected day, collapsed) and `ratings` (per movie: mine, summary, saving, error).

1. **Components never mutate state.** They dispatch an event (`daySelected(7)`) or call an effect.
2. **Events are past tense** (`ratings/submitted`, `ratings/saved`) and are listed in `state/events.ts`.
3. **The reducer is pure** and unit-tested.
4. **Async work lives in `state/effects.ts`.** For example, rating a movie is optimistic: `ratings/submitted` updates the UI right away, then the effect dispatches `ratings/saved` on success, or `ratings/failed` to roll back.

### Styling: design tokens

`ts/apps/web/src/styles/tokens.css` is the single place to change the look.

- **Palette** colours are named after the colour (`--color-blood`, `--color-bone`).
- **Role** tokens are named after their use (`--accent`, `--text`, `--bg-panel`, `--border`).

Component CSS uses role tokens only. The comment package's CSS uses the same role tokens, with fallbacks for apps that don't define them.

**Fonts are self-hosted** in `public/fonts` (Bebas Neue for display, Inter for body, both under the Open Font License) and preloaded in `index.html`. The hero title is sized for narrow Bebas Neue and overflows in any fallback font, so that face uses `font-display: block`: the browser briefly waits for it instead of flashing the wrong font. Don't switch back to a third-party font service.

### The haunted house

The house at the bottom of the sidebar is a stage (`ts/apps/web/src/components/house/`) that plays one of several short **stories**, picked at random on each page load. Add `?story=<id>` to the URL to watch a particular one (for example `?story=run-for-it`).

- **The stage** (`HouseScene.tsx`) draws the trees, fog and house. Stories draw into two layers: *inside* the windows (behind the window bars) and *outdoors* (over the ground, behind the big trees). They can also open and shut the door.
- **A story** (`stories/*.tsx`) is a `defineStory({ id, title, loop, still, frameAt, Inside, Outside })`. `frameAt(t)` is a pure function from seconds to what to draw, so every beat is unit-tested. Shared geometry and helpers (door and window positions, `groundY`, easing) are in `scene.ts`, and reusable characters (the stick figure, `runAcross`, `standAt`) are in `actors.tsx`.
- **To add one:** write `stories/<name>.tsx`, add it to `STORIES` in `stories/index.ts`, and run the tests. `stories/contract.test.tsx` checks every registered story: unique id, and a seamless loop that starts and ends on the story's still frame (no characters showing; the door may be open or shut).
- **Stories so far:** `run-for-it` (a stick figure dashes in, peeks out and flees; something with a knife rises in the attic) and `abduction` (a TV watcher is beamed up into a hovering UFO; the door he left open swings shut).
- **Cost:** about 2 KB of JavaScript. The clock only re-renders when the frame changes, stops completely while the house is scrolled out of view (then resumes where it left off), pauses in background tabs, and never runs for visitors who prefer reduced motion.

## Infrastructure decisions

These were decided in September 2026. The goals were **about $0/month**, **little setup and upkeep**, **keeping Cloudflare** since it already hosts DNS, and a **real Go server** rather than Go compiled to WebAssembly.

| Decision | Choice | Why | Rejected alternatives |
| -------- | ------ | --- | --------------------- |
| **DNS** | Cloudflare (unchanged) | Already the domain's DNS. Proxied records give free TLS, CDN and DDoS protection. | — |
| **Site hosting** | Cloudflare Pages | Free, global CDN, same vendor as DNS. A Pages Function gives same-origin `/api`. | GitHub Pages (previous host; no server-side proxy) |
| **API hosting** | Google Cloud Run, `us-central1` | Runs a normal Go container at $0 (free tier: 2M requests, 180k vCPU-s and 360k GiB-s per month). Scales to zero, with Go cold starts well under a second. Official Terraform provider. Reuses the Firebase project's GCP account. | Go→Wasm on Cloudflare Workers (not wanted); Cloudflare Containers ($5/mo); Fly.io, Railway, DigitalOcean ($2–5/mo); Oracle free VM or IONOS VPS (server to maintain); Vercel (serverless Go, non-commercial free tier) |
| **Database** | Neon Postgres, free plan | Managed Postgres at $0 (0.5 GB, 100 CU-hours/month). Scales to zero after 5 min idle. No server to run. | Cloud SQL (~$8–10/mo); Firestore (not SQL, read quotas); Turso; self-hosted Postgres on a VM |
| **Images** | Cloudflare R2 + custom domain | 10 GB free, **no egress fees**, cached at Cloudflare's edge. Posters are no longer part of the site build, and the app bundle (without Firebase) is ~76 KB gzipped. | Firebase Storage; bundling images |
| **Anti-spam** | Cloudflare Turnstile | Free, privacy-friendly, usually invisible. Terraform creates the widget and passes the secret to the API. | reCAPTCHA; nothing |
| **Container builds** | `ko` | Builds a ~6 MB image straight from Go source. No Docker or Dockerfile needed, locally or in CI. | Docker; Cloud Build |
| **Infrastructure as code** | Terraform, state in GCS | One `terraform apply` creates everything below. GCS gives state locking with no extra service. | Manual console setup; Pulumi |
| **Deploys** | `Makefile` + scripts, run by GitHub Actions *and* locally | The same commands everywhere; CI adds nothing a laptop can't do. | CI-only pipelines |
| **CI auth to GCP** | Workload Identity Federation | Keyless: no long-lived Google keys stored in GitHub. | Service-account JSON key |

**Cold starts:** when both Cloud Run and Neon are idle, the first request of a visit can take roughly 1–2 seconds. That first request is the `page_view` analytics call, so movies load right behind it. To keep the API always warm, set `min_instance_count = 1` in `infra/gcp.tf`, which costs a few dollars a month.

**Cost guardrails:**
- Cloud Run is capped at 2 instances.
- Artifact Registry keeps only recent images (under the 0.5 GB free storage).
- Neon's free plan has hard limits rather than overage billing.
- An optional GCP budget alert is available (`billing_account_id` in `terraform.tfvars`).

**One cost to watch:** Cloud Run → Neon traffic counts as internet egress. The free tier covers 1 GB/month from North America, and this API's responses are small JSON.

### What Terraform manages (`infra/`)

| File | Resources |
| ---- | --------- |
| `cloudflare.tf` | DNS for the apex and `www`, the Pages project and its custom domains (with `API_ORIGIN`), the R2 bucket, `images.` custom domain, Turnstile widget |
| `gcp.tf` | Enabled APIs, Artifact Registry (with cleanup), Secret Manager secrets (DB URL, visitor secret, Turnstile secret), the Cloud Run service and runtime service account, Workload Identity Federation for GitHub, the deployer service account, optional budget alert |
| `neon.tf` | The Neon project, `main` branch, `spooky` database and role |
| `outputs.tf` | Writes `deploy.env` and `ts/apps/web/.env.production`. Both hold public identifiers only, and both are committed. |

Secrets never live in the repo. Terraform moves them straight into Secret Manager, and Cloud Run reads them from there. The credentials needed to *run* Terraform come from the environment: `CLOUDFLARE_API_TOKEN`, `NEON_API_KEY`, and Google's application-default credentials.

**Division of labour:**
- **Terraform owns the long-lived resources.**
- **Deploys ship code:**
  - `make deploy-api` runs `ko build` then `gcloud run deploy`.
  - `make deploy-web` runs `vite build` then `wrangler pages deploy`.
- **Terraform ignores the Cloud Run image**, so deploys and `terraform apply` never fight over it.

## First-time setup

You do this once. After it, every push to `main` deploys automatically.

1. **Install tools:** `gcloud`, `terraform`, Go and Node. Then log in with `gcloud auth login && gcloud auth application-default login`.
2. **Enable billing on the GCP project** (`nightsofhorror-50265`). The Cloud Run free tier requires a linked billing account, but it's still $0 within the free tier.
3. **Create API tokens:**
   - **Cloudflare API token** with these permissions:
     - Account: *Cloudflare Pages: Edit*, *Workers R2 Storage: Edit*, *Turnstile: Edit*
     - Zone (`31nightsofhorror.com`): *DNS: Edit*, *Zone: Read*
   - **Neon API key** (Neon console → Account settings → API keys).

   ```bash
   export CLOUDFLARE_API_TOKEN=... NEON_API_KEY=...
   ```
4. **Remove the old GitHub Pages DNS records.** In the Cloudflare DNS dashboard, delete the apex `A`/`AAAA` records (185.199.x.x) and the `www` record that point at GitHub Pages. Terraform creates the replacements.
5. **Bootstrap and create everything:**

   ```bash
   ./scripts/bootstrap.sh   # creates the Terraform state bucket, backend.hcl and terraform.tfvars
   make infra               # review the plan, then type "yes"
   make upload-posters      # posters → R2
   make deploy              # API → Cloud Run, site → Cloudflare Pages
   ```
6. **Commit the generated files:** `infra/backend.hcl`, `infra/terraform.tfvars`, `deploy.env`, `ts/apps/web/.env.production` and `infra/.terraform.lock.hcl`.
7. **Set up GitHub:**
   - Add the repository secrets `CLOUDFLARE_API_TOKEN` and `NEON_API_KEY`.
   - Create a `production` environment (optionally with required reviewers).
   - Turn off GitHub Pages in the repo settings.
8. **Optional, one-off: bring over the old Firestore ratings** with `make import-firestore-ratings`.
   - It's best effort and safe to re-run.
   - Old ratings count toward averages but aren't linked to anyone's new visitor cookie.
   - After that, the Firebase project's Firestore and Auth can be switched off.
